# 课程扩展架构方案（草案，待裁定，非实施）

> 依据：四账号总指令“432 节是 V1 规划非上限，扩展架构先定方案再分独立 PR 改造”。
> 本文件仅为方案草案，不改任何课节文件、台账与代码；实施须经裁定后分独立 PR 进行。
> 基线：main 679895e0；审定证据：P0/P1/P2 72/72 真实运行验证（见 course-audit-72-summary.md）。

## 原则（硬约束）
1. 不破坏现有 432 节 ID、单元归属、进度与作品数据；扩展只做加法，不 renumber、不改名、不移动现有课节。
2. 不在审定中擅自重构所有运行器；现有运行器（Python 标准库、turtle 坐标模拟、pygame）保持不动，新引擎以注册方式接入。
3. 每项扩展先有方案、再有独立 PR、再有真实运行证据与 CI；不以文档数量代替可玩课程。
4. V2 视觉冻结不变；新内容复用现有组件与视觉语言，冲突只报差异不擅改。

## 审定中发现的扩展动因（有证据）
1. 详案结构双轨：P0 为 v1 结构（objectives/learningSteps/courseState/runtimeVerified），P1/P2 为 v2 结构（learningOutcome/teachingSteps/status）。
   扩展前须先定“课节记录结构版本化”规则，否则新内容无法与旧内容同表统计。
2. 评估执行状态：P2-U1-L01 assessment executionStatus 为 spec_only（仅规约未执行）。
   扩展须要求新增课节的评估用例可执行（本次实审方法：正向 + 边界反例双向验证），spec_only 不得作为完成证据。
3. 元数据标签错位：P2-U2 focusConcept 与实际内容系统性错位。
   扩展须加元数据校验门：focus/概念标签须与 learnerBuild 实际内容一致，否则 PR 不过审。
4. 领域缺口（P0–P2 切片）：AI 应用、数据库深层、机器人与硬件、移动端在 P0–P2 内无实质内容；
   跨语言衔接的 Blockly/Scratch/C++ 段在其他路线分工内，不在本方案内擅自补写。

## 扩展方式（加法清单）
1. 新单元/新路线以独立单元文件与独立课节 ID 段接入，复用现有台账结构（lesson-task-register 追加行，不整文件重写）。
2. 新引擎（如数据库练习、硬件模拟）以“引擎注册表”接入：登记引擎名、运行方式、验证方法、失败模式；不改现有引擎实现。
3. 新评估用例一律要求可执行：正向断言 + 至少一个边界/反例断言；mutation 式验证（故意改错须有测试失败）作为推荐做法。
4. 跨语言衔接：新增衔接课节时须标注“从 X 语言概念到 Y 语言概念”的映射关系，不得只贴两段代码。

## 实施顺序（建议）
1. 先定课节记录结构版本化规则与元数据校验门（小 PR，不动现有课节内容）。
2. 再补 2 项内容缺陷修正（P0-U1-L01、P2-U1-L01）与 P2-U2 标签修正（独立小 PR，待独立教研后）。
3. 再按领域缺口优先级立新单元方案（每领域先出覆盖矩阵与综合项目目标，再动手写课）。
4. 全量 432 节的扩展总矩阵待其余路线（Hark A/B/C 分工）审定后汇总，本方案不代评他账号范围。

## 不做事项
- 不重编号、不合并、不删除现有课节；不整文件覆盖公共台账；不改 V2 冻结规范；不伪造试学与教研证据。
