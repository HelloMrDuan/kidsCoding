## 三、本课的积木（学生可用）

| 积木 | 对应 Scratch 原生 opcode | 说明 |
|---|---|---|
| 当绿旗被点击 | `event_whenflagclicked` | 帽子 |
| 重复执行 N 次 | `control_repeat` | 复习与应用 |
| 将 x 设为（在 **A** 到 **B** 之间取随机数） | `motion_setx`，输入是嵌套的 `operator_random` | 本课新积木。**一块里有两个数字（下界、上界）**，生成工程时展开成真实的"设置 x"里嵌套"取随机数" |

编译出的工程用的是 Scratch VM 原生 opcode，随机数由真实的 `operator_random` 产生。沙箱不模拟任何积木的行为。

**真实 VM 的行为（已在安装的 scratch-vm 5.0.300 源码里核对）**：`operator_random` 对调换的上下界取小的当下界；两个数都是整数时返回整数且**两端都包含**；随机源是 `Math.random()`。本课积木限定整数。

## 四、判定为什么必须读"上下界"，而不是只看结果

随机结果会骗人。要求范围是 ±180 时，上下界写错的程序，10 次取值**碰巧**都落在 ±180 以内的概率（整数上下界，两端都包含，每次取值独立；按 `(范围内整数个数 / 总整数个数)^10` 计算）：

| 孩子写的上下界 | 10 次全部碰巧落在 ±180 内的概率 |
|---|---|
| -300～300 | 0.6% |
| -240～240 | 5.7% |
| -200～200 | 35.0% |
| -190～190 | 58.3% |
| -181～181 | 94.6% |

如果只看这 10 个结果，"差一点点"的错误上下界在多数运行里都会"通过"，换一次运行又不通过，孩子学不到任何东西。

所以判定**同时读两样真实运行数据**，都来自沙箱对真实 VM 的观察：

1. 每一次真实 `operator_random` 调用收到的 `FROM`、`TO` 和返回值；
2. 每一次真实 `motion_setx` 之后礼物的 x。

结果只用来展示"这一次运行"；**"上下界是否限定在要求范围内"这条结论只由上下界决定**，不受运气影响。

## 五、三层判定（每次运行同时输出，措辞沿用 L02 的统一口径）

| 层 | 内容 | 通过条件（提议） |
|---|---|---|
| 舞台结果 | 这一次 10 次（及以上）礼物出现的 x，哪些落在要求范围内 | 每一次的 x 都在本关要求范围内 |
| 任务结果 | 礼物有没有真的出现在不同的位置 | 范围内，并且至少出现 `minDistinctPositions` 个不同的位置（写死一个数不算） |
| 知识证据 | 程序用了取随机数，而且它的上下界限定在要求范围内、并且没有窄到失去随机的意义 | 每一次随机的上下界都在要求范围内，且上下界之间的宽度不小于要求范围宽度的 `minSpreadShare` |

"理解情况"固定一句："系统只能看到这一次运行的行为，看不出你是否明白为什么这样限定上下界——需要进一步解释或练习。"**任何结果都不写"已掌握"。**
一关通过 = 任务结果与知识证据同时通过（与 L02 相同）。

## 六、四关与提议参数

舞台 x 范围 -240～240。要求范围用 `allowedMin / allowedMax`。

| 关 | 层 | 内容 | 要求范围 | 说明 |
|---|---|---|---|---|
| 1 猜一猜 | 探索与预测 | 固定演示：`重复 10 次，将 x 设为 -300～300 之间的随机数`（只读） | 观察用，不判过 | **故意用过宽的上下界**。先预测"10 次里礼物会不会跑到舞台外面"，再运行看真实结果。演示关用**固定种子**（见下） |
| 2 自己搭 | 独立挑战 | 让礼物每次出现在舞台上的随机位置，不超出左右各留一点的范围 | -180～180 | 对应详案 |
| 3A 换成右半边 | 迁移 | 礼物只出现在舞台右半边 | 0～180 | 孩子要改下界，而不是照抄 |
| 3B 只在中间 | 迁移 | 礼物只出现在舞台正中间一小块 | -60～60 | 范围变窄，随机的"宽度"要求随之变化 |

**演示关的固定种子**：演示关要让每个孩子看到"同样的 10 个位置"，这样预测才有确定的答案、也能在测试里验证。做法是沙箱在**这一次运行**里把 `Math.random` 换成带种子的随机数发生器，运行结束立即恢复；真实 VM 的 `operator_random` 照常执行。**自己搭的三关不用种子，每次运行都真的不一样**。界面会明说这一点（"演示关的随机数用了固定种子，每个人看到的 10 个位置一样；你自己搭的关卡每次都不一样"）。种子取 **7**（算法：mulberry32 种子随机数发生器 → 按 Scratch 的 `operator_random` 整数规则 `low + floor(r × (high + 1 − low))`）。我用独立的 Python 程序在 -300～300 上算出前 10 次取值是 `[-293, -263, 287, 120, 13, -57, -20, -156, 32, 138]`：有 3 次明显跑出舞台（|x| > 240），7 次在 ±180 以内。这串数由三处互相独立地验证：Python 计算、TypeScript 单测、**真实 VM 在沙箱里实际取出的值**（E2E），三者必须一致，不凭记忆。

提议数值（全部集中在 `params.ts`，状态 `proposed`）：

| 参数 | 提议值 | 说明 |
|---|---|---|
| 舞台 x 范围 | -240～240 | Scratch 舞台 |
| 要求重复次数 | 至少 10 次取值 | 详案"重复 10 次" |
| 重复次数上限 | 1～20 | 沙箱上限 |
| 上下界范围（输入限制） | -500～500，整数 | **要让孩子能写出错误的范围并看到后果**，所以输入范围比要求范围宽 |
| 积木上限 | 8 块（不含帽子）、嵌套 1 层、3 条脚本 | |
| `minDistinctPositions` | 3 | 10 个位置里至少 3 个不同；窄范围（如 0～5）也基本满足 |
| `minSpreadShare` | 0.5 | 上下界宽度不小于要求范围宽度的一半 |
| 单次运行帧上限 | 150 | |

## 七、教学定向范围与诚实的评测缺口

- 只能判断"这一次运行的上下界和结果是否满足要求"，不能判断孩子是否理解"为什么要限定上下界"。
- 本课的随机数在真实 VM 里产生，但沙箱**没有渲染器**：真实 Scratch 在有渲染器时会把越界的角色挤到舞台边缘（只露一部分），没有渲染器的沙箱里 x 就是 x。所以本课**不说"礼物看不见了"**，说"超出了本关要求的范围 / 已经在舞台之外"，并在舞台上把越界的位置画成红色标记。
- 不评价开放创作；"随机选择不同礼物造型"（详案的拓展）本课不做，沙箱只提供一个造型。
