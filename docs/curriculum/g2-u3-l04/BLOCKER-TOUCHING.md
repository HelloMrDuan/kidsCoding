# G2-U3-L04《判断碰撞得分》：开工前发现的技术分叉（需首席裁定）

状态：**等待首席裁定，尚未开发**。分支 `kiro/p0-g2-u3-l04`（从 main 切出，与 #494 无关）。

## 事实（可复核）

本课的核心是"小球碰到篮子才加分"，也就是 Scratch 的 `sensing_touchingobject`（碰到……？）放进 `control_if`。

1. scratch-vm@5.0.300 的 `RenderedTarget.isTouchingSprite()` 在 `this.renderer` 不存在时**直接返回 false**（`scratch-vm.js` 中该函数的开头：`if (!firstClone || !this.renderer) return false`）。
2. 本仓库所有 Scratch 沙箱（G2、L02、L03）都**没有渲染器**，这是有意的：沙箱用 `connect-src 'none'`、不加载 `scratch-render`、不绘制画面。
3. 用真实 VM 做了探针：`probe-touch-without-renderer.cjs`（在 `apps/web` 下运行 `node` 即可复现）。两个角色放在同一点 (0,0) 完全重叠，`if 碰到篮子 then 将 x 设为 99`，运行后球的 x 仍是 0，`isTouchingSprite('篮子')` 为 false。结论：**在现有沙箱里，真实的"碰到"积木永远判不到碰撞**。

所以 L04 如果照 L02、L03 的方式（真实 VM、不模拟积木行为）直接做，"碰到篮子才得分"这一核心在运行时永远不会得分，三层判定会全部失败。这不是调参能解决的。

## 可选方案（利弊，不替首席选）

| 方案 | 做法 | 优点 | 风险 / 代价 |
|---|---|---|---|
| A. 引入渲染器 | 沙箱加载 `scratch-render`（目前只是 scratch-vm 的传递依赖，不是 `package.json` 的直接依赖），让真实的 `touching` 工作 | "碰到"是真实 VM 行为，最符合"真实执行"的原则 | 需要 WebGL/canvas，沙箱 CSP 和资源要改；CI 的无头 Chrome 是否稳定要验证；包体积、新增直接依赖要评审；共享沙箱约束可能被打破 |
| B. 用坐标比较代替 | 本课改教"用 x、y 坐标之差判断是否够近"（`如果 |球 x - 篮子 x| < 30`），不用 `touching` 积木 | 无需渲染器，沿用现有沙箱，真实 VM 执行 `operator_*` 与 `control_if` | 教学上换了知识点（碰撞检测 → 用坐标判断距离）；与目录"碰到篮子"的字面不一致，要首席改目录 |
| C. 沙箱里补一个"碰到"的最小实现 | 沙箱在 VM 之外实现一个几何碰撞函数，覆盖 `isTouchingSprite` | 积木还是 `touching` | 这是**模拟积木行为**，违背"不用模拟代替真实执行"；不建议 |

我的倾向是 B（风险最小、仍是真实执行），但它改变了教学内容，A 才是原样保留教学内容。**这是教学与架构取舍，需首席裁定。**

## 不依赖该裁定、可以先做的部分

计分的另一半是"同一个球不重复计分"（目录里的失败情形：循环多次检测导致连加 3 分），即**状态标记 / 隐藏已接小球**。这部分用 `control_if`、变量和 `looks_hide` 就能在无渲染器的 VM 里真实执行，不受上面问题影响。裁定之前我只会推进这一半的教学方案，不写任何依赖碰撞检测的代码。
