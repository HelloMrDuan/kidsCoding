# KidsCoding CI 执行统一标准

> 适用范围：所有 Muse 账号、所有课程方向、所有功能开发、所有 PR。
> 牵头：负责主要架构和 CI 的账号；其他账号继续各自课程方向，不得改变四账号原有职责分工，不得覆盖其他账号的分支和提交。
> 本文件是执行标准，不是某一次故障的复盘；一次故障的复盘见各 PR 的证据记录，不得把本文件当作已修复某 Job 的证明。

## 0. 目标与硬限制

- 单个 GitHub Actions Job 目标耗时不超过 **12 分钟**。
- **15 分钟为当前已确认的硬限制**（见 `.github/workflows/curriculum-content.yml` 多个 Job 的 `timeout-minutes: 15`），不得将其作为正常目标。
- 预留至少 **3 分钟安全余量**：目标 12 分钟 + 余量 3 分钟 = 硬限制 15 分钟。
- 所有必需测试必须执行，不能通过跳过测试、删除测试、降低断言、`continue-on-error` 换取 CI 通过。
- PR 可以按风险执行必要测试子集，但不能将未执行的测试伪装成通过；发布门禁必须有完整回归证据。

## 1. Job 超时预算

1. 新 Job 在设计时就要给出预算：预估测试数 × 历史单测耗时 ÷ workers + 检出、安装依赖、构建、启动服务的时间。
2. 预算超过 12 分钟时，设计阶段就要拆分，不得先合入再等超时。
3. 已有 Job 实测超过 12 分钟时，记入第 9 节整改清单，按优先级拆分，不得只把 `timeout-minutes` 延长来掩盖。
4. `timeout-minutes` 本身不是目标：把它从 15 改到 20 或 30，只能凭拆分后的实测数据申请，且必须同时说明为什么拆分后仍需更长时限，不得单独以延长时限作为修复。
5. 任何 Job 不得设无限重试，不得把失败设为 `continue-on-error`。

## 2. 测试分片和分配规则

1. 按**历史耗时均衡**分片，不是按文件数、不是按测试数、不是按字母顺序。
2. 一个文件内测试数过大、单文件耗时过大时，必须先把该文件按 describe / 课程 / 功能域拆成多个 Job，不得让一个文件整 file 落在一个分片里拖垮该 Job。
3. Scratch/Blockly 必须独立分片，不得把全部 Scratch/Blockly 测试塞进一个 Job。
4. Python 课程按课程和运行环境分组；AI 模型测试把轻量检查与真实训练分离；数据库集成测试隔离数据库资源。
5. 每个分片必须独立执行并独立上传报告，分片名、测试文件列表、测试数必须在 Job 日志和报告里可查。
6. 分片调整后，必须重新核对分片覆盖：所有必需测试无遗漏、无重复。覆盖检查见第 8 节。

## 3. worker 数量与资源隔离

1. worker 数量要写在 Job 里，不得只依赖框架默认值；默认值随框架版本变化，不可作为预算依据。
2. 提高 workers 不是万能：同时启动多个 Chrome / VM / 构建进程会争 CPU、内存和端口，必须实测单测耗时是否反而拉长。
3. 资源隔离规则：
   - 每个 Playwright 测试用独立 browser context / page，不得跨测试共享已登录状态、IndexedDB、localStorage；
   - 数据库集成测试每个 Job 用独立数据库 / schema，不得共享同一库；
   - 共享的 dev / prod 服务不得被测试通过可变状态互相影响；需要共享状态的测试必须在标准里单独说明并加锁或串行。
4. workers、Chrome、VM、构建的资源上限要在 Job 设计里写明，超限时先降并发、再拆分片，不得先延长时限。

## 4. 测试耗时采集

1. 每个 Playwright Job 必须采集单测试耗时，至少包括：测试名、文件、开始时间、结束时间、耗时、结果、worker。
2. 采集方式优先用 reporter，不改业务测试代码：
   - `playwright.config.ts` 统一加 `line` + `json` reporter（json 输出到 `test-results/`，随 artifact 上传）；
   - 或新增自定义 reporter，打印 `START / END` 时间戳；
   - 不得只用默认 dot reporter 作为超时诊断依据：dot 只在完成时出点，取消时无法反推在跑哪两个测试。
3. 单元测试（vitest）按模块分组输出耗时，慢测试（单测超过 30 秒）必须在报告里单独列出。
4. 耗时数据是分片预算的唯一依据：没有历史耗时数据的新测试，首次合入时按最保守估计（同类测试最大耗时）算预算。

## 5. 日志和测试报告

1. 每个 Job 取消或失败时，必须能从日志和报告里直接回答：哪个测试失败、哪个测试在跑、耗时多少、失败证据在哪。
2. 每个分片 `if: always()` 上传报告和截图，不得只在成功时上传。
3. 报告命名必须含分片名，不得多个分片共用同一个 artifact 名互相覆盖。
4. 日志里不得出现密钥、PAT、签发 URL；上传的报告里不得含真实儿童个人信息、真实账号密码。

## 6. 失败分类与有限重试

失败必须先分类，再决定处理，不得一律重跑：

| 分类 | 特征 | 处理 |
| --- | --- | --- |
| 断言失败 | 某个测试明确失败，有失败名和断言证据 | 修代码或修测试，不重跑碰运气 |
| 代码异常 | 崩溃、类型错误、未捕获异常 | 修代码，不重跑 |
| 环境故障 | 依赖安装失败、Chrome 安装失败、服务起不来、网络不可达 | 修环境或重试一次，并记录环境证据 |
| Job 超时 | 作业被 runner 取消，无单个测试失败，只有取消错误 | 按第 9 节做超时诊断，不得直接重跑；重跑前必须先拉作业日志和单测耗时 |

重试规则：

- 同一 Job 同一失败原因最多重跑 **1 次**用于验证环境波动，且必须在 PR 里写明重跑原因和上一次日志结论；
- 超时类失败在没有耗时证据和拆分方案前，不得重跑；
- 不得用 `rerun-failed-jobs` 把已通过的 Job 再跑一遍，不得用全量重跑掩盖单个分片问题。

## 7. PR、夜间和发布门禁

- PR 门禁：与 PR 改动直接相关的测试子集必须通过；未执行的测试必须在 PR 正文里如实列明，不得写成已通过。
- 夜间门禁：全量回归在夜间或发布前执行，输出完整覆盖证据和耗时对比。
- 发布门禁：必须有完整回归证据（全部必需 Job 通过、全部测试数与覆盖清单一致），且独立人工复核（课程类）或设计复核（页面类）已完成；缺任何一项不得标记发布。
- 所有门禁的 Job 都适用 12 分钟目标和 15 分钟硬限制，夜间回归也不例外：夜间 Job 同样要拆分，不得靠夜间不限时来逃避拆分。

## 8. 全量测试覆盖完整性检查

1. 每次分片调整后，必须用 `--list`（Playwright）或等价清单核对：调整前测试总数 = 调整后各分片测试数之和，且无重复测试名。
2. 覆盖清单要随 PR 提交：分片名、文件列表、测试数、实测耗时。
3. 覆盖检查失败（遗漏或重复）时，该 PR 不得合并，即使各分片都显示通过。
4. 单元测试、组件测试、Playwright、数据库测试分别做覆盖清单，不得用一类测试的通过冒充另一类。

## 9. CI 超时自动诊断和处理流程

超时发生时，按以下顺序处理，不得跳步：

1. **只读拉日志**：拉被取消 Job 的作业级日志，确认前置步骤是否通过、测试步骤开始时间、最后输出时间、取消时间。
2. **确认测试数和耗时**：从日志里取 `Running N tests`、点数批次、总耗时；从上一次成功运行取同 Job 的总耗时和余量。
3. **确认分片失衡**：对比各分片的测试数和耗时；分片 1 远大于分片 2 时，先怀疑分片规则，不先怀疑单个测试。
4. **确认单测试超时**：检查 `test.setTimeout`、expect 超时、下载 / 导入 / VM 加载超时；单测试超时应当报失败，不应当静默数分钟。
5. **定位在跑测试**：只有 line/json reporter 的 START/END 时间戳才能定位；dot reporter 的点数只能推断队列位置，不能作为确证。
6. **给出拆分方案**：按历史耗时拆分片、调整 workers、或按文件 / describe 拆 Job；方案必须含预算（拆分后各分片预估耗时）和覆盖清单。
7. **验证顺序**：先跑拆分后的单分片，确认耗时和报告；再跑完整 CI，确认同一头上全部通过；最后才更新 PR 正文和合并判断。

## 附录 B：各 Muse 接手任务时的检查清单

接手任何任务前，先读本文件，然后回答：

1. 我改动的文件会触发哪些 Job？（按 workflow 的 paths 列表核对）
2. 这些 Job 里我涉及的测试有多少个、历史耗时多少、落在哪个分片？
3. 我的改动会不会让某个分片超过 12 分钟？超过时，我的 PR 里是否已经拆分？
4. 我的分片报告是否独立上传、命名是否含分片名？
5. 失败时，我能否说出具体测试名和失败证据，而不是只说“CI 红了”？
6. 我的 PR 正文是否如实列明已执行和未执行的测试？

任何一项回答为“不知道”时，先补盘点，不得先合入。
