## 三、各类工作属于谁

1. **课程自身代码、内容、素材与课内测试**：归长期路线负责人；其他账号只按明确授权进行有限改动或非作者审核。
2. **共享 LessonWorkspace 和工作区 UI**：由主 Muse 按唯一产品 Task-ID 授权；2 号承担既有共享外壳、插槽、响应式与适配接口工作，课程作者仅维护本课内容/适配层。具体文件责任见工作区 OWNERSHIP.md。
3. **全局架构、视觉 token、台账、共享 CI、workflow 和目录冲突**：由主 Muse 协调唯一文件所有权和合并顺序；主号也不能绕过 PR 和独立审核。
4. **旧工程资产**：保留真实作者、PR、commit 与测试；曾经代审或代开发不意味着长期所有权转移。
5. **并发边界**：每执行账号同时最多一个主要课程开发 PR；全团队至多三个新课程主要开发 PR。待审课程 PR 超过 2 个，暂停认领新课，优先排障审核合并。

## 四、审核和验收

- 2 / 3 号课程：默认由 **4 号非作者工程复核**，主 Muse 集成验收。如 4 号参与了该课代码，另指定实际非作者。
- 4 号课程：默认由 **主 Muse 第一工程复核**，必要时由 2 / 3 号独立交叉复核。
- 主 Muse 自己写的代码：由未参与改动的 2 / 3 / 4 号复核，严禁自审。
- 多个 Muse 会话若共用 GitHub 身份，则 PR 评论中的 COMMENTED/PASS 可记录内部复核证据，**不等于 GitHub APPROVED**；如分支保护要求真正批准必须遵守。
- PR 必须唯一 Task-ID、真实代码/测试、必需 CI、非作者审核和可核实 merge/main CI。未验证不得报告通过；作者不得擅自合并。
- AI 工程审查、自动测试和浏览器 CI 不代替独立人工教研、有监护人同意的儿童试学及正式发布批准。工程已合并仍应保持诚实的 in_review / outline_not_playable，不能自动标记 completed。

## 五、启动前置门禁

- **R0（2 号）**：须有可信硬件/仿真环境、安全范围、作品和可复现验收；当前只保留资产/计划。
- **C0/C1（4 号）**：先通过安全隔离的编译运行方案、资源限制和浏览器/受控运行实测；不能直接执行儿童代码于宿主机。
- **P3（4 号）**：先核对交接和旧 PR，防止重复开发。
- **A1（4 号）**：新课程缺正式详案/判定合同/先修依据时先审定后实现；已合并的他人课程不因此重做。
- **P0/P1/P2（主号）**：72 节真实 Python 运行审定仅是审定事实；进入正式网页开发需逐任务明确实施者。
- **G2（3 号）**：必须复用历史 Scratch VM / 浏览器试验与交接资产，不得将 Node 运行结果当作真实浏览器 E2E。

## 六、唯一依据与变更控制

1. 长期课程归属以本文件为唯一汇总；根目录 AGENTS.md 管工程协作规则，工作区 OWNERSHIP.md 只管组件文件边界。
2. 实时完成情况以 main 的课程台账、已合并 PR 和真实 CI 为准；历史审定是证据，不是最新任务状态。旧账号名称不得再次用作现行角色。
3. 只有项目负责人明确裁定、独立 PR + CI + 审核 + 合并生效，才能改变路线归属。暂停一条路线、历史审核他人课程、换账号平台均不算迁移责任。
4. 新账号首次接入必须阅读本文件、AGENTS.md、分阶段计划和课程台账。过去对话与现行文件冲突时，以最新已合并文件为准。
5. 相关文件：[产品总纲](./README.md)、[分阶段计划](./02-PHASED-DELIVERY.md)、[课程台账](./lesson-task-register.json)、[任务执行规则](./11-TASK-EXECUTION-POLICY.md)、[工作区文件责任](../product/p0-kitten-workspace/OWNERSHIP.md)。
